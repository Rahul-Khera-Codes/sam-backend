# Billing & Pricing Page

## What it does
A redesigned Billing page (`/dashboard/settings/billing`) that replaces the old hardcoded 5-tier pricing table with 4 plan cards (Free Trial, Starter, Growth, Enterprise) plus a feature-comparison table grouped by AI Employee, matching a new design mockup. Behind the visual change are real capabilities that didn't exist before: a Stripe-backed 14-day free trial, in-app plan switching between all three paid plans, per-plan minute caps tunable via `.env`, and — as of the production rollout — real subscription enforcement that pauses Marketing/Sales/HR actions (never calls) when a business falls behind on payment. The "Professional" tier was dropped entirely (confirmed zero subscribers on it, 2026-10-01). **Enterprise is fully self-serve** at a fixed $999/mo with unlimited minutes — not sales-assisted (an earlier draft of this doc said otherwise; reversed 2026-10-01 per explicit decision).

## Key files

**sam-backend**
- `backend/app/routers/billing.py` — all billing endpoints + Stripe webhook handlers.
- `backend/app/schemas/billing.py` — request/response models.
- `backend/app/core/config.py` — Stripe price IDs, per-plan minute limits, trial length, grace period length (all env-tunable).
- `backend/app/core/billing_gate.py` — `get_access_status(business_id)` / `require_active_subscription(business_id)`, the shared subscription-enforcement gate. **Never used on phone-call handling.**
- `backend/.env` / `backend/.env.example` — the actual tunable values.
- Endpoints: `GET /billing/subscription`, `POST /billing/create-checkout-session`, `POST /billing/change-plan`, `POST /billing/customer-portal`, `POST`/`DELETE /billing/addons/executive-agent`, `POST /billing/webhook`.
- Gated endpoints (reject with 402 once `access_status == "blocked"`): `marketing.py::create_marketing_scheduled_post` / `publish_marketing_post_now`, `sales.py::create_lead_lookup`, `competitor_agent.py::generate_competitor_report`, `market_agent.py::trigger_refresh`, `hr_careers.py::submit_application`, `hr_interviews.py::create_public_interview_live_session` (the latter two are public/candidate-facing — gated anyway per explicit decision, see below).

**ai-employees-app**
- `src/pages/dashboard/Billing.tsx` — orchestrator: owns subscription state, per-action loading state, and wires handlers to the API client.
- `src/components/billing/plans.ts` — typed plan definitions and the grouped feature-comparison data.
- `src/components/billing/ctaResolver.ts` — pure function deciding each plan card's button label/action/disabled-state from the current subscription. All three paid plans (Starter/Growth/Enterprise) go through the same checkout/switch logic.
- `src/components/billing/{PlanCards,PlanCard,PlanComparisonTable,UsageSummaryCard,CurrentPlanCard,AddonCard}.tsx` — presentation components, all built on the shared shadcn `Card`/`Table` primitives (the old page hand-rolled divs and a raw `<table>` instead).
- `src/components/dashboard/SubscriptionStatusBanner.tsx` — dashboard-wide (not just the Billing page) amber/red banner shown once a previously-subscribed business goes `grace`/`blocked`, wired into `DashboardLayout.tsx`.
- `src/lib/voiceAgentApi.ts` — `getBillingSubscription`, `createCheckoutSession`, `changePlan`, `createCustomerPortalSession`, `enable/disableExecutiveAgentAddon`.
- `src/pages/Signup.tsx` — trial-length marketing copy ("Start your 14 day free trial"); keep in sync with `TRIAL_PERIOD_DAYS` manually if it ever changes, there's no shared source of truth between the two.

**DB migration**: `supabase/migrations/20261001072032_businesses_subscription_grace_period.sql` adds `businesses.subscription_past_due_since` — needed for the grace-period gate. Everything else still derives from Stripe's own subscription object via the existing webhook.

## Decisions / tradeoffs

- **Trial mechanism**: `plan="trial"` in `CreateCheckoutSessionRequest` resolves internally to the real Starter price with `subscription_data.trial_period_days` attached on the Stripe Checkout Session — not a separate $0 product. This means it auto-converts to paid Starter when the trial ends, with zero extra webhook/sync logic: the existing `customer.subscription.updated` handler already re-reads price/status/limits off the subscription regardless of why it changed.
- **Trial's minute cap (60) is a read-time override, not stored.** `_handle_subscription_upsert` (the webhook handler) only ever knows about *price*, and trialing-Starter and active-Starter share the same price. Rather than teach the webhook to also branch on status (which would leave a stale "60" in the DB for a moment after Stripe flips `trialing → active`, until another webhook corrects it), `GET /billing/subscription` computes `plan_name="Free Trial"` / `minute_limit=settings.plan_trial_minute_limit` on the fly whenever `status == "trialing"`. No new write path, no stale-state window.
- **Minute limits moved out of a hardcoded `PLAN_KEY_MAP` literal into `Settings`** (`plan_starter_minute_limit`, `plan_growth_minute_limit`, `plan_trial_minute_limit`), mirroring how Stripe price IDs were already configured. Lets these be retuned via `.env` without a code change.
- **Professional tier dropped entirely** — removed from `PLAN_KEY_MAP`, `Settings` (`stripe_pro_price_id` deleted), and all frontend copy. Confirmed no current subscribers before removal.
- **Enterprise is fully self-serve** at a fixed $999/mo (not "$999+"/negotiated as originally designed) with `plan_enterprise_minute_limit=None` meaning unlimited — reversed from the original "Talk to sales, sales-assisted only" design on 2026-10-01. It goes through `PLAN_KEY_MAP`/`create-checkout-session`/`change-plan` exactly like Starter/Growth, no special-casing. The old `mailto:` CTA path was removed from `ctaResolver.ts` entirely (dead code once Enterprise became self-serve).
- **`minute_limit: null` means unlimited, not zero.** `BillingSubscription.minute_limit` is typed `number | null` on the frontend; `UsageSummaryCard`/`CurrentPlanCard` explicitly check `== null` and render "Unlimited" instead of a 0-capped progress bar. Don't `?? 0` this field — that silently turns "unlimited" into "0 minutes allowed," which is backwards.
- **Subscription enforcement (grace period, then block)**: `access_status` (`"ok" | "grace" | "blocked"`) is computed server-side in `billing_gate.get_access_status()` and returned on `GET /billing/subscription` — the frontend never computes this itself, it just renders what the backend says. `active`/`trialing` → `ok`. `past_due` → `grace` for `subscription_grace_period_days` (default 5) from the first time the webhook saw it go `past_due` (stamped in `subscription_past_due_since`, not reset by repeat webhook deliveries), then `blocked`. `canceled` or no subscription at all → `blocked` immediately — except a business that's simply never subscribed yet doesn't get the alarming dashboard banner (only a business that *had* one and lost it does; `SubscriptionStatusBanner` checks `has_subscription` first).
  - **Phone calls are never gated** — this was an explicit, deliberate decision. `agent/agent.py` has zero billing checks and that's intentional, not an oversight.
  - **Gated actions were scoped deliberately narrow**: only the write/create actions that trigger a paid external API call or real compute (Marketing post creation, Sales' three research-run endpoints, HR's resume-scoring-triggering application + interview session start) — not reads, not settings, not anything that would prevent a blocked business from seeing their own data or fixing billing.
  - **HR's two gated endpoints are candidate-facing, not dashboard-facing** (`submit_application`, `create_public_interview_live_session` — no `user_id`/`verify_business_access`, `business_id` derived from the job/join-token instead). Hard-blocking them means a job candidate can see a 402 if the business they're applying to is behind on payment — flagged explicitly and kept anyway per an explicit decision to match Marketing/Sales exactly, not an oversight.
  - `hr_interviews.py::_raise_domain_error` gained an `isinstance(exc, HTTPException)` passthrough at the top — without it, the gate's 402 would've been swallowed by that function's broad `except Exception` and re-raised as a generic 502, hiding the real reason.
- **Plan-tier feature gating (separate from payment-status enforcement above)**: `billing_gate.require_plan_feature(business_id, feature)` checks whether the business's CURRENT plan tier includes a feature at all, independent of whether they're paid up. `FEATURE_MIN_TIER` matches the comparison table exactly — `marketing`: any plan (incl. trial/Starter), `sales`/`hr`: Growth or Enterprise, `executive_agent`: Enterprise only (tier resolved from `stripe_price_id` against `settings.stripe_growth_price_id`/`stripe_enterprise_price_id` — trial rides on the Starter price so it naturally resolves to the same tier as Starter). All 6 previously payment-gated endpoints (`marketing.py` ×2, `sales.py`, `competitor_agent.py`, `market_agent.py`, `hr_careers.py`, `hr_interviews.py`) now call `require_plan_feature(...)` instead of `require_active_subscription(...)` directly — it calls the payment check internally first, then the tier check. Blocks immediately for anyone on an insufficient plan, no grandfathering (explicit decision, 2026-10-01).
- **Executive Assistant addon — intentionally left alone for now.** `executive_agent` is defined in `FEATURE_MIN_TIER` but not wired to any endpoint. The existing addon purchase gate (`enable_executive_agent_addon` in `billing.py`, predates this session, ADR 0001) lets any paid plan buy it, which conflicts with the comparison table's "Enterprise only" claim — explicitly deferred per the user, not silently changed. `AddonCard.tsx` shows an "Under development" badge next to it so this is visible in the UI while the decision is pending.
- **Platform staff get free, permanent Enterprise access on their own businesses.** `billing_gate.is_platform_admin_business(business_id)` returns true if any `super_admin` on that business also holds platform-super-admin status (a `super_admin` role on the fixed "AI Employees Inc. Platform" business, `type='platform'` — the same mechanism that gates Mission Control/impersonation, see `app/core/auth.py::verify_platform_super_admin`). Deliberately **not** a hardcoded business-ID or email list — reusing the existing role means any business owned by a current or future platform-super-admin is automatically covered, no manual list to maintain. Today this covers Sam's "AI Employees inc.", Charles's "Mr. Barber", and Rahul's "Woyce Tech" — each platform staff member's own personal testing/demo business (distinct from the "AI Employees Inc. Platform" admin business itself).
  - `get_access_status` short-circuits to `("ok", None)` for these businesses before any Stripe-status read; `require_plan_feature`'s tier check short-circuits similarly (treated as Enterprise tier) — both bypassed regardless of whatever's actually in Stripe for that business (including nothing at all).
  - `GET /billing/subscription` (`billing.py::get_subscription`) also overrides the response for these businesses — `plan_name="Enterprise"`, `status="active"`, `minute_limit=None` (unlimited) — so the Billing page UI matches what's actually granted, rather than showing "no subscription" while every feature silently works regardless.
  - Verified directly (read-only, via the running container): all three real businesses resolve `is_platform_admin_business=True` / `access_status="ok"` / `require_plan_feature("sales")` unblocked despite two of them having no real Stripe subscription at all; 5 unrelated businesses (including one — "Divinity DJs" — whose owner had platform-super-admin **revoked** in a later migration) correctly resolve `False`/`blocked`, confirming the exemption is scoped precisely and respects revocation.
- **`change-plan` doesn't write to `businesses` itself.** `stripe.Subscription.modify(...)` fires `customer.subscription.updated`, and the existing webhook handler already re-syncs the row from that event — adding a second write path in the new endpoint would just be two places updating the same columns. The practical consequence: a `GET /billing/subscription` called immediately after `change-plan` returns may briefly show the pre-switch plan. The frontend (`Billing.tsx`'s `handlePlanAction`) handles this by polling `getBillingSubscription` up to 3 times, 1.5s apart, after a successful plan change, rather than trusting one immediate re-fetch.
- **Repeat-trial guard**: `create-checkout-session` rejects `plan="trial"` if the business already has a `stripe_customer_id` (only ever set once a checkout actually completes) — blocks a business from getting a second free trial after canceling or converting.
- **Base-item identification in `change-plan`** matches the subscription item by its current `price.id` (falling back to the first item if no match), rather than assuming index 0 — robust against the Executive Agent add-on existing as a second subscription item.
- **No in-app plan switch during an active trial** (known v1 limitation). A trialing subscriber's price is always Starter's, and modifying price on a trialing subscription has real Stripe nuance around whether it ends the trial early — that UX decision wasn't specified, so `ctaResolver.ts` deliberately shows a disabled "Available after trial" hint on other plans during `status="trialing"` rather than inventing trial-interruption behavior. A trialing user who wants to switch early can still use "Manage Plan" → Stripe Customer Portal.
- **Visual language**: kept the app's existing Inter font and shadcn/Tailwind semantic tokens rather than the mockup's Lexend/Figtree Google Fonts and raw hex CSS variables, for consistency with the rest of the dashboard.
- **Feature-comparison content was verified against the shipped product**, not copied verbatim from the mockup. One row was corrected: HR's interview claim is "AI audio interviews with scoring rubric" (not "video & audio") — candidates are audio-only today, no camera track is published.
